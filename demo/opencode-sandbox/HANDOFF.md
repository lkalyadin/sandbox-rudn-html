## 1. Задача

Развернуть OpenCode v2 с веб-интерфейсом на внешнем VPS как демо-стенд для урока
**«Визуализация данных с помощью AI»**, студенты экономического факультета.

Условия:

- Студенты работают **только через браузер**: один адрес, один пароль, логин `opencode`.
- Студенты **видят сессии друг друга** — это осознанное допущение, не баг.
- 20–30 одновременных студентов. Сервер: 4 vCPU / 8 ГБ (подтвердить), диск ~100 ГБ.
- У сервера **только IP, домена нет**.
- Студенты **не имеют доступа к файловой системе** сервера. Всё, что создаёт агент,
  студент получает **ссылкой**, клик по которой запускает скачивание в его браузере.
- Агент должен «из коробки» знать: что он песочница для экономистов, какие внешние
  ресурсы ему доступны, как готовить файлы. Оформляется как **дефолтный навык +
  системный промпт** (см. §7).
- Модели — бесплатные из коробки, креды не нужны. Для приёмки:
  `opencode/deepseek-v4.1-flash-free`.

**Готово, когда:** приёмочный тест из §12 проходит целиком.

## 2. Доступ и роли — прочти внимательно, тут главный подвох

Ты работаешь **без root**. Пользователь root имеет.

1. Ты **генерируешь себе SSH-ключ** и выдаёшь пользователю **публичную** часть.
   Он добавляет её в `authorized_keys` выделенного пользователя **на время
   развёртывания**, после приёмки — удаляет.
2. Root-команды ты **не выполняешь**, а выдаёшь пользователю отдельным блоком:
   «выполни под собой» (см. §10).
3. **Главная развилка.** Чтобы работать с Docker, нужно членство в группе `docker`.
   Но членство в `docker` — это **фактически root на хосте**: через контейнер можно
   смонтировать `/etc` и прочитать что угодно. Это надо сказать пользователю прямо,
   а не проскочить молча. Варианты:

   - **A (рекомендуется).** Выдать `docker` на время развёртывания, после приёмки —
     убрать. Стенд продолжит работать сам: у контейнеров `restart: unless-stopped`.
   - **B.** Пользователь сам выполняет **все** docker-команды по твоим инструкциям.
     Работает, но это десятки итераций «скажи — выполнил — покажи вывод».

   Из варианта A не делай вид, что «root не давали». Назови вещи своими именами.

## 3. Архитектура: 4 слоя изоляции

```
Интернет ──► edge (nginx, порты 80/443, TLS от Let's Encrypt)
              │
              ├── /            → sandbox:4096     (веб-UI OpenCode, пароль на входе)
              └── /files/      → workspace/ ro    (скачивание результатов, тот же пароль)

sandbox (OpenCode, runtime=runsc) ──┐
   сеть sandbox_net: internal, БЕЗ маршрута наружу
   read-only rootfs, cap_drop ALL, no-new-privileges, лимиты CPU/RAM/PIDs
                                   │
egress (tinyproxy, allowlist) ─────┴── egress_out: единственный выход в интернет
```

- **Слой 1 — сеть.** У песочницы нет маршрута в интернет вообще. Наружу только через
  `egress` с белым списком доменов (`FilterDefaultDeny Yes`).
- **Слой 2 — контейнер + gVisor.** `--runtime=runsc`: изоляция на уровне отдельного
  ядра, а не только namespaces. Плюс read-only rootfs, сброс capabilities.
- **Слой 3 — правила OpenCode.** `permissions` и `policies`. **Это НЕ песочница:**
  документация прямо говорит, что `shell` выполняется с правами пользователя хоста,
  а разбор команды — best effort. Относись как к ремням безопасности, а не к стене.
- **Слой 4 — edge.** Наружу торчит только nginx с паролем.

### Что за «утилита» помимо Docker

- **gVisor (`runsc`)** — то самое «ещё что-то». Ставится пользователем под root.
- **tinyproxy** — прокси с белым списком (в `egress/`).
- **nginx + certbot** — входная точка и TLS.

## 4. Проверенные факты — не перепроверяй, это стоило токенов

Всё ниже проверено **запросами к живому серверу**, а не чтением документации.

### OpenCode

- Версия в проде: **2.0.32**. Установка: `curl -fsSL https://opencode.ai/v2/install | bash`
  → бинарь в `~/.opencode/bin/opencode` (`OPENCODE_INSTALL_DIR` через pipe не работает).
- **v1 использовать нельзя:** в его веб-UI воспроизводимо падали Settings и New session.
- Пароль: **`OPENCODE_SERVER_PASSWORD`**, логин **всегда** `opencode`.
  `--password` и `opencode service set password` в v2 не нужны.
- Ответ без кредов: `401` **с `www-authenticate: Basic realm="Secure Area"`**.
  То есть basic-auth работает, и браузер показывает окно входа сам.
- Флаг `--print-logs` — чтобы логи уходили в stdout (в Docker это `docker compose logs`).
- Запускать не из `$HOME`, иначе ловится `failed to initialize fff`. У нас `WORKDIR /work`.

### Бесплатные модели (креды НЕ нужны)

```
провайдер:  id = opencode                      ← именно так, не opencode-free
            apiKey = "public"                  ← буквально строка public
            baseURL = https://opencode.ai/inference/openai/v1
каталог:    https://models.opencode.ai/api.json
            кэшируется в ~/.cache/opencode/models.json (232 провайдера)
дефолт:     big-pickle
стоимость:  0 у всех
```

Доступные (проверено): `big-pickle`, `deepseek-v4.1-flash-free`, `glm-5.3-flash-free`,
`longcat-2.5-preview-free`, `mimo-v2.6-flash-free`, `space-bunny-free`, `beam-free`.

> **Следствие для сети:** каталог берётся с `models.opencode.ai`, а **не** с `models.dev`
> (я на этом ошибся, потом исправил). Оба домена OpenCode обязаны быть в allowlist, иначе
> студенты увидят пустой список моделей.

### Правила (v2 отличается от v1!)

- Ключ называется **`permissions`** (массив правил `{action, resource, effect}`),
  а не `permission`. Эффекты: `allow`, `deny`, `ask`. **Последнее совпавшее правило
  выигрывает.**
- Действия в v2: `shell` (**не** `bash`), `read`, `edit`, `glob`, `grep`, `subagent`
  (**не** `task`), `skill`, `question`, `webfetch`, `websearch`, `external_directory`,
  `execute`. `doom_loop` и `lsp` — не действия v2.
- Ключ **`policies`** — жёсткий запрет (`tool.use`, `provider.use`, `integration.use`).
  Отличие принципиально: правило из `permissions` студент снимает кнопкой «Allow always»,
  `policies` — нет.
- Другие полезные ключи: `share: "disabled"` (иначе сессию можно выложить публичной
  ссылкой!), `tool_output` (обрезка вывода), `media.image` (лимиты картинок),
  `model`, `update: "disable"`.
- **Лимита на размер произвольных (не картиночных) файлов в OpenCode нет.** Это
  закрывается только квотой на каталог (см. §9).
- Схема конфига всегда доступна: `https://opencode.ai/config.json`.
  Документация v2: `https://opencode.ai/v2/docs/` (разделы `/permissions/`, `/policies/`).

### Что ещё проверено про интерфейс

- `GET /api/fs/read/<путь>` → `200`, корректный `content-type`, `accept-ranges: bytes`.
  То есть скачать файл можно и из UI, под своим паролем.
- `GET /api/provider`, `/api/model`, `/api/info` — рабочие, нужен basic-auth.

## 5. Внешние ресурсы: что открыть и чего нельзя ломать

Файл: `egress/allowlist` (уже заполнен). Требование пользователя — только необходимое:

```
# OpenCode: модели и каталог — БЕЗ НИХ СТЕНД НЕ РАБОТАЕТ
(^|\.)opencode\.ai$
(^|\.)models\.opencode\.ai$

# Учебные датасеты
(^|\.)github\.com$                    # репозиторий prasertcbs/basic-dataset
(^|\.)codeload\.github\.com$          # скачивание zip/tar
(^|\.)raw\.githubusercontent\.com$    # отдельные raw-файлы
(^|\.)objects\.githubusercontent\.com$
(^|\.)openml\.org$
(^|\.)archive\.ics\.uci\.edu$
(^|\.)huggingface\.co$
(^|\.)datasets-server\.huggingface\.co$
(^|\.)cdn-lfs\.huggingface\.co$       # бинарные LFS-файлы HF
(^|\.)cdn-lfs-us-1\.huggingface\.co$
(^|\.)hf\.co$
```

Три правила, которые здесь легко нарушить:

1. **Не сломать бесплатные модели.** Домены `opencode.ai` и `models.opencode.ai`
   обязаны остаться. Бесплатные модели — это сетевые вызовы, а не локальный инференс.
2. **Egress ограничивается только у контейнеров.** Сборка образов идёт через сеть
   хоста, там ограничений нет — это нормально, так и задумано.
3. **Никаких CDN для JS.** `cdn.jsdelivr.net`, `unpkg.com` и подобные сознательно
   закрыты. Значит графики в HTML должны быть **самодостаточными** (PNG в base64
   или inline SVG). Это надо написать агенту в навык, иначе он будет упорно
   подключать plotly с CDN и удивляться.

Диагностика: `docker compose logs egress | grep -i blocked` покажет заблокированный
домен. Добавил домен → `docker compose restart egress`.

## 6. Как студент получает созданные файлы

Два независимых пути — оба уже реализованы в каркасе.

**Путь 1 — из интерфейса.** UI показывает содержимое проекта, API отдаёт файлы
(проверено, см. §4).

**Путь 2 — страница `/files/`** (гарантированный, от UI не зависит):

```
http://<IP>/files/
```

Реализация: `workspace/` примонтирован в контейнер edge **только на чтение**,
`autoindex on`, каждый файл отдаётся с `Content-Disposition: attachment`
(+ `X-Content-Type-Options: nosniff`), служебные файлы с точки закрыты.

Почему именно `attachment`, а не «пусть открывается»: `/files/` — тот же origin, что
и UI, а UI хранит пароль в `localStorage`. Если бы HTML из рабочей папки отрисовывался,
студент мог бы выложить туда страничку с JS и вычитать чужой пароль.

Пароль — **тот же**, что у OpenCode: `edge/htpasswd` генерируется в `scripts/30-up.sh`
из `SANDBOX_PASSWORD` (`openssl passwd -apr1 -stdin`, чтобы пароль не светился в `ps`).
Логин `opencode`. Браузер запомнит после первого ввода.

> **Что должен делать агент внутри стенда:** складывать результаты в `output/` и в
> ответе давать ссылку вида `http://<IP>/files/output/<имя файла>`. Это прописывается
> в навык (§7). Без этого требование «ссылка, которая начинает скачивание» не выполняется.

## 7. Знания агента: дефолтный навык + системный промпт

Нужно, чтобы агент **знал по умолчанию**: зачем он существует, что ему доступно,
как готовить файлы. Три механизма, применить все:

1. **Навык (skill).** Топ-ключ `skills` есть в схеме конфига. Точный формат каталога
   навыков сверь в `https://opencode.ai/v2/docs/skills/` (я его не проверял вживую).
   Ожидаемо — каталог с `SKILL.md`, подкладывается в системный конфиг (монтируется
   read-only в контейнер рядом с `config/opencode.json`).
2. **Инструкции.** Ключ `instructions` в конфиге — список файлов, которые подмешиваются
   в контекст. Сюда же `AGENTS.md` в рабочей папке (`workspace.template/AGENTS.md`).
3. **Свой агент по умолчанию.** Ключи `agents` + `default_agent`, если нужно, чтобы
   промпт применялся всегда, а не только когда модель решит вызвать навык.

### Содержание навыка (заготовка, не сокращай смысл)

```markdown
# Кто ты

Ты — песочница агентной разработки для студентов экономического факультета.
Урок называется «Визуализация данных с помощью AI». Твоя задача — помогать
студенту загружать учебные данные, считать по ним статистику и делать понятные
визуализации. Объясняй шаги простым языком: студенты экономисты, а не программисты.

# Что тебе доступно в интернете

Только эти ресурсы (остальное заблокировано на уровне сети, бесполезно пытаться):
- GitHub-репозиторий учебных датасетов: https://github.com/prasertcbs/basic-dataset
  (в нём готовые CSV: superstore, bike_sharing, netflix_titles, world_happiness,
  seattle_airbnb, video_games, airline_satisfaction, flight_delay и другие)
- openml.org — репозиторий датасетов
- archive.ics.uci.edu — классические датасеты UCI
- huggingface.co и datasets-server.huggingface.co — датасеты Hugging Face

Если чего-то нет в списке — считай, что этого нет вовсе. Не предлагай студенту
источники, которые не откроются. Доступ идёт через прокси: используй стандартные
клиенты (requests, urllib, pandas.read_csv) — они уважают HTTP_PROXY сами.

# Чего делать НЕЛЬЗЯ

- Подключать внешние JS/CSS с CDN. cdn.jsdelivr.net, unpkg.com и подобные
  заблокированы. Графики в HTML делай самодостаточными: PNG в base64
  (matplotlib) или inline SVG. Один HTML-файл, никаких внешних зависимостей.
- Выполнять sudo, ssh, mount, ставить пакеты, ходить в интернет куда-то ещё.
- Пытаться выйти за пределы рабочей папки.

# Как отдавать результат студенту

1. Складывай результат в `output/`.
2. Давай студенту готовую ссылку: `http://<IP>/files/output/<имя файла>`
   → клик по ней скачивает файл в его браузер. Других способов получить файл
   у студента нет: к файловой системе он доступа не имеет.
3. В конце ответа напиши, что сделал, простыми словами.

# Как готовить файлы

Главное правило: **HTML обязан быть самодостаточным**. Никаких ссылок на внешние
JS/CSS: они не загрузятся, и страница у студента будет пустой.

- График через matplotlib: PNG в base64 или inline SVG, подписанные оси, заголовок,
  подписи на русском. Самый надёжный путь, всегда работает.
- График через plotly: **только** `fig.write_html(path, include_plotlyjs=True)`.
  По умолчанию plotly пишет `include_plotlyjs='cdn'`, и график не появится вовсе.
- Интерактив через Chart.js или D3: вставь содержимое файла из `/opt/viz/` прямо
  внутрь `<script>...</script>` в HTML.
- Altair не используй: он по умолчанию тянет vega с CDN.
- Таблица: маленькая — прямо в HTML; большая — отдельным CSV в `output/`.
- Данные из xlsx/parquet сначала приводи к CSV, чтобы не гонять тяжёлые форматы.
- Если датасет большой — не грузи его целиком в контекст, считай через pandas
  в скрипте и показывай студенту только итог.
```

Дополнительно в `docker-compose.yml` передай агенту адрес стенда, чтобы он мог
собирать ссылки, — например, переменной окружения `PUBLIC_URL=http://<IP>` и
подстановкой в навык при развёртывании.

### Библиотеки для визуализации: предустановить в образ

Ставить на этапе **сборки образа**, а не в рантайме: у песочницы интернета нет,
`pip install` запрещён политикой, pypi в allowlist не открыт. Сборка идёт через
сеть хоста — там ограничений нет.

**Python:**

```dockerfile
RUN pip install --no-cache-dir \
      pandas numpy matplotlib seaborn scipy \
      openpyxl pyarrow statsmodels plotly
```

`openpyxl` и `pyarrow` нужны потому, что учебные датасеты попадаются в xlsx и parquet.

**JS — «лёгкие» версии, вшиваются в образ** (например, в `/opt/viz/`):

| Библиотека | Файл | Размер | Когда брать |
| --- | --- | --- | --- |
| Chart.js | `chart.umd.min.js` | ~200 КБ | основной выбор: лёгкая и достаточная |
| Plotly basic | `plotly-basic.min.js` | ~1 МБ | интерактив, но не полный бандл (он ~3.5 МБ) |
| D3 | `d3.v7.min.js` | ~280 КБ | кастомные графики |

Скачать их удобно на этапе сборки (npm-реестр или jsdelivr) — тогда они попадают
внутрь образа. **В allowlist их добавлять не нужно и не следует:** в рантайме
песочнице эти домены не нужны, а открывать npm из стенда — лишний supply chain.

Две тихие поломки, которые здесь вероятнее всего:

1. **Plotly по умолчанию использует CDN.** `include_plotlyjs='cdn'` — дефолт, при
   закрытом CDN страница откроется пустой, без ошибки. Отсюда обязательное
   `include_plotlyjs=True`.
2. **Altair** по умолчанию тянет `vega`, `vega-lite` и `vega-embed` с CDN. Либо
   настраивать локальные бандлы, либо просто не использовать.

Про `plotly-basic.min.js` стоит сказать отдельно: это официальный неполный бандл
(базовые типы графиков), он в разы легче полного и для учебной визуализации обычно
хватает. Если агент делает страницу через plotly, `include_plotlyjs=True` вставит
полный бандл — тогда HTML потянет ~3.5 МБ. Это нормально (файл скачивается, а не
грузится по сети), но если хочется совсем лёгких страниц — путь через Chart.js.

В `workspace.template/inline_chart.py` уже лежит готовый шаблон: он вшивает
содержимое `/opt/viz/<файл>.js` в страницу и защищает от преждевременного закрытия
тега `<script>`. Агенту проще скопировать шаблон, чем угадывать самому.

**Проверка в приёмке:** в полученном HTML не должно быть `src="https://` или
`href="https://`. Если есть — страница у студента будет пустой.

## 8. TLS: Let's Encrypt на голый IP

Это работало не всегда, поэтому факты:

- С **15 января 2026** Let's Encrypt выдаёт сертификаты на IP-адреса
  (General Availability).
- Такие сертификаты **обязаны** быть короткоживущими: профиль **`shortlived`**,
  срок ~**160 часов (~6.7 суток)**. Продлить срок нельзя.
- Проверка домена — HTTP-01 на **порту 80**.
- Certbot это поддерживает. Точное имя флага сверь сам:
  `certbot --help all | grep -i profile` (ожидаемо `--preferred-profile shortlived`).

### План

Порт 80 занят нашим nginx → проверку отдаём через webroot, а не освобождаем порт:

1. nginx уже умеет `location /.well-known/acme-challenge/ { root /var/www/acme; }`
   (в `edge/site.tls.conf`). Том `/var/www/acme` общий с certbot.
2. Отдельный сервис `certbot` (образ `certbot/certbot`) с томами
   `/etc/letsencrypt` и `/var/www/acme`, запуск:
   `certonly --webroot -w /var/www/acme -d <IP> --preferred-profile shortlived --agree-tos -m <email>`
3. **Deploy hook**: копирует `fullchain.pem` и `privkey.pem` в `edge/certs/`
   и делает `nginx -s reload` (через `docker compose exec edge nginx -s reload`).
   Копировать именно файлы, а не симлинки: симлинки из `live/` не переживают
   монтирование томов.
4. **Продление**: свой цикл, каждые 12 часов `certbot renew --quiet`
   (в контейнере `entrypoint` через `sleep`-цикл либо host-таймером).

### Риск, о котором надо сказать

Срок жизни 6.7 суток. Если продление сломается, стенд умрёт **в течение недели**.
Обязательно: проверка «сертификат не старше 6 дней» в мониторинге и понятная
инструкция, как продлить руками. Это не «поставил и забыл», как с 90-дневными.

Альтернатива, если продление окажется хрупким: заменить edge на **Caddy** — он
сам делает ACME и продление. У нас уже написан nginx с `/files/`, так что это
запасной путь, а не первый.

## 9. Обслуживание: очистка и квота на `work/`

### Ночная очистка

Диск 100 ГБ, папку чистим раз в сутки ночью. Делает **пользователь под root**
(ты без root). Вариант через systemd — надёжнее cron:

```ini
# /etc/systemd/system/opencode-cleanup.service
[Unit]
Description=Ночная очистка рабочей папки стенда OpenCode

[Service]
Type=oneshot
# Чистим СОДЕРЖИМОЕ, не удаляя сам каталог (он смонтирован как точка монтирования).
ExecStart=/usr/bin/find /srv/opencode/workspace -mindepth 1 -delete
```

```ini
# /etc/systemd/system/opencode-cleanup.timer
[Unit]
Description=Запуск очистки стенда ночью

[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true
Unit=opencode-cleanup.service

[Install]
WantedBy=timers.target
```

```bash
systemctl daemon-reload && systemctl enable --now opencode-cleanup.timer
```

Замечание: `-mindepth 1 -delete` не удалит саму точку монтирования — это правильно.
Если каталог не точка монтирования, а обычный (без квоты), можно `rm -rf` содержимое.

### Квота

Диск 100 ГБ, папке можно дать широкую квоту (например 60 ГБ). Самый надёжный способ,
не зависящий от файловой системы хоста, — файл-образ ext4:

```bash
# под root, ОДИН раз
mkdir -p /srv/opencode
truncate -s 60G /srv/opencode/workspace.img
mkfs.ext4 -q -F /srv/opencode/workspace.img
mkdir -p /srv/opencode/workspace
mount -o loop /srv/opencode/workspace.img /srv/opencode/workspace
# чтобы примонтировалось после перезагрузки
echo '/srv/opencode/workspace.img /srv/opencode/workspace ext4 loop,defaults 0 2' >> /etc/fstab
# владелец должен совпадать с SANDBOX_UID/SANDBOX_GID из .env
chown 1001:1001 /srv/opencode/workspace
```

Затем в `docker-compose.yml` каталог `./workspace` заменяется на
`/srv/opencode/workspace` (или делается симлинк `workspace → /srv/opencode/workspace`).
Учти: uid контейнера и владелец каталога обязаны совпадать — это проверяет
`scripts/00-preflight.sh`.

Альтернатива без loop-устройств: если overlay2 лежит на xfs с `pquota`, хватит
`StorageOpt: size=60G`. Проверить ФС: `df -T /var/lib/docker`.

## 10. Root-команды для пользователя (чеклист)

Выдавай так, готовым блоком. Замени `<user>` на имя выделенного пользователя,
`<IP>` — на адрес VPS.

```bash
# 1) Выделенный пользователь (без sudo!) и каталог стенда
useradd -m -s /bin/bash <user>
mkdir -p /srv/opencode && chown <user>:<user> /srv/opencode

# 2) SSH-ключ агента на время развёртывания (.ssh/authorized_keys создать при необходимости)
#    Публичную часть агент выдаст сам.
#    После приёмки: удалить строку и перезапустить sshd (или просто убрать ключ).

# 3) Docker + Compose
apt-get update
apt-get install -y docker.io docker-compose-v2 openssl ca-certificates
usermod -aG docker <user>          # ВНИМАНИЕ: это фактически root на хосте.

# 4) gVisor (та самая «утилита»)
curl -fsSL https://gvisor.dev/archive.key | gpg --dearmor -o /usr/share/keyrings/gvisor-archive-keyring.gpg
echo "deb [arch=amd64 signed-by=/usr/share/keyrings/gvisor-archive-keyring.gpg] https://storage.googleapis.com/gvisor/releases release main" > /etc/apt/sources.list.d/gvisor.list
apt-get update && apt-get install -y runsc
runsc install                       # регистрирует runtime в /etc/docker/daemon.json
systemctl restart docker
runsc --version

# 5) Квота на work/ — команды из §9 (loop-ext4).
# 6) Ночная очистка — юниты и timer из §9.
# 7) Порты 80/443 должны быть открыты снаружи (проверить у провайдера/ufw).
```

После этого **выйти и зайти заново** (членство в группе `docker` применяется при
новом входе) — и ты сможешь работать.

## 11. Порядок развёртывания

1. Сгенерировать SSH-ключ, отдать публичную часть пользователю, дождаться доступа.
2. Проверить `uname -a`, `nproc`, `free -h`, `df -h`, `sudo -n true` (должно падать),
   `docker info | grep -i runtime`, `runsc --version`, наличие `/dev/kvm`
   (если KVM нет — gVisor пойдёт на `systrap`, это нормально).
3. Разложить каркас в `/srv/opencode` (или `~/opencode-sandbox`), создать `.env`
   из `.env.example`: `SANDBOX_PASSWORD`, `SANDBOX_UID/GID`, `EDGE_PORT`, `ENABLE_TLS`,
   `PUBLIC_URL`.
4. Добавить в `docker-compose.yml`:
   - `runtime: runsc` для сервиса `sandbox`;
   - лимиты: `mem_limit: 6g`, `cpus: 3.0`, `pids_limit: 512`;
   - сервис `certbot` и общий том `/var/www/acme`;
   - монтирование `/srv/opencode/workspace` вместо `./workspace`.
5. Прогнать `scripts/00-preflight.sh` — он ловит несовпадение uid, отсутствие docker
   и несуществующий тег образа.
6. Проверить тег базового образа OpenCode (на живом сервере был **2.0.32**, в
   каркасе может стоять 2.0.0):
   `docker run --rm --entrypoint sh ghcr.io/anomalyco/opencode:2.0.32 -c 'opencode --version'`

   Заодно посмотреть, какая там база: `cat /etc/os-release`. Если **Alpine** —
   научные Python-пакеты на musl ставятся больно. В этом случае бери за основу
   `python:3.12-slim-bookworm` и ставь OpenCode внутрь официальным скриптом
   (`curl -fsSL https://opencode.ai/v2/install | bash`), а не тащи Python в Alpine.
7. Подложить навык и промпт (§7), подставить `PUBLIC_URL` в текст ссылок, добавить
   в образ Python-библиотеки и JS-библиотеки для графиков (§7, «Библиотеки»).
8. Поднять: `scripts/30-up.sh` (он же генерирует `edge/htpasswd`).
9. `scripts/50-verify-isolation.sh` — обязательно, и читать **эффекты**, а не «юнит
   запустился». Проверить: из песочницы не открывается `example.com`, но открывается
   `opencode.ai` и `raw.githubusercontent.com`; `~/.ssh` недоступен; rootfs read-only.
10. Выпустить сертификат (§8) и проверить, что `https://<IP>/` открывается без
    предупреждений браузера.
11. Приёмочный тест (§12).
12. Сказать пользователю, что можно удалять SSH-ключ и забирать `docker`-группу.

## 12. Приёмочный тест (сценарий пользователя)

Прогоняй не «на глаз», а через CLI внутри контейнера — так воспроизводимо:

```bash
docker compose exec -u sandbox sandbox \
  opencode run --model opencode/deepseek-v4.1-flash-free "<промпт>"
```

| # | Промпт / действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | «Какие сейчас новости в мире?» | **Не может**: доступа к произвольному интернету нет. Агент должен сказать, что ограничен, а не выдумывать факты. |
| 2 | «Какие внешние ресурсы тебе доступны?» | Перечисляет ровно список из навыка: GitHub `prasertcbs/basic-dataset`, openml, UCI, Hugging Face. |
| 3 | «Найди на этих ресурсах небольшой датасет, скачай его» | Скачивает, например, CSV из `prasertcbs/basic-dataset`. Проверить: `docker compose logs egress \| grep -i blocked` — **пусто**. |
| 4 | «Сделай одностраничный HTML с простой визуализацией этих данных» | Создаёт `output/<файл>.html`, график виден. **Проверить, что в файле нет `src="https://` и `href="https://`** — внешних зависимостей быть не должно, иначе у студента страница будет пустой. |
| 5 | Агент даёт ссылку `http://<IP>/files/output/<файл>.html` | Открыть в браузере снаружи → **начинается скачивание** (не открытие), файл открывается локально и график видно. |
| 6 | Открыть `http://<IP>/` в браузере | Показывается UI, спрашивает пароль, вход `opencode` + `SANDBOX_PASSWORD`. |
| 7 | Задать в UI тот же вопрос, что в п.3 | Работает и через веб-интерфейс, стриминг ответа идёт. |

Пункт 5 — это ровно требование «ссылка, которая начинает скачивание». Если открывается
просмотр вместо скачивания — сломался `Content-Disposition: attachment` в `edge/site.*.conf`.

## 13. Честные ограничения и риски — скажи о них пользователю

1. **`permissions`/`policies` — не песочница.** Документация OpenCode сама пишет, что
   `shell` работает с правами пользователя хоста, а разбор команд best effort.
   Пример: разрешённый `python3 *` пропускает и `python3 -c "..."`, то есть любой код.
   Настоящая граница — контейнер + gVisor.
2. **Членство в `docker` = root на хосте.** Отсюда рекомендация: давать на время
   развёртывания и убирать после.
3. **Бесплатные модели — общая квота.** `apiKey` у них буквально `public`. 20–30
   студентов в одну квоту могут ловить `429`. Лечится своими кредами или
   ограничением скорости на прокси.
4. **Сертификат живёт ~6.7 суток.** Продление обязано работать, иначе стенд умрёт за
   неделю. Нужен мониторинг.
5. **Один пароль на всех, сессии видны всем, рабочий каталог общий.** Это допущение
   пользователя, но следствие надо назвать: студент может удалить чужие файлы
   (ночной очистки для этого мало).
6. **gVisor — не панацея.** Он ловит побег из контейнера, но не спасает от «агент
   делает глупости внутри». Плюс возможны несовместимости по syscall; проверяй на месте.
7. **`/files/` без пароля выкладывал бы файлы наружу.** Пароль обязателен, и это тот
   же пароль, что у OpenCode.
8. **Нагрузка.** Один процесс `opencode serve` на всех студентов. Лимиты
   (`mem_limit`, `cpus`, `pids_limit`) обязательны, иначе один шумный студент уронит
   стенд остальным.

## 15. Мелочи, которые уже стоили времени — не наступай снова

- `pkill -f "opencode serve"` **убивает свою же SSH-сессию**, потому что паттерн
  совпадает с текстом собственной команды. Не используй `pkill -f`.
- Caddy (если вернёшься к нему): `auto_https off` ломает TLS, нужен
  `auto_https disable_redirects`; при доступе по IP нужен `default_sni <IP>`.
- Порт сайта в прокси не должен совпадать с портом upstream — иначе
  `address already in use`.
- `WorkingDirectory` нельзя оставлять `$HOME` (см. §4).
- В user-systemd **harden-директивы почти не работают**: `ProtectHome`,
  `InaccessiblePaths`, `IPAddressDeny` юнит запускают, но эффекта нет (проверено
  измерением). Работают только `MemoryMax`/`CPUQuota`/`TasksMax` и `NoNewPrivileges`.
  Именно поэтому нужен Docker с root, а не «изоляция через systemd».
- `kernel.apparmor_restrict_unprivileged_userns=1` (Ubuntu 24.04+) запрещает
  unprivileged user namespaces → без root не будет ни rootless podman, ни bwrap.
- Проверка через `systemd-run -p X` **возвращает успех, даже когда ограничение
  не применяется.** Всегда проверяй эффект, а не факт запуска.
